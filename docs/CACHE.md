# Lab 2: кешування (cache-aside)

## Що кешується і як

Кешується найчастіше читання: список постів `GET /posts` (у сценарії навантаження
це 4 з 10 запитів кожної ітерації). Код: [`app/cache.py`](../app/cache.py),
[`app/routers/posts.py`](../app/routers/posts.py).

Схема **cache-aside**:

1. API шукає відповідь у Redis за ключем `posts:list:limit=<l>:offset=<o>:author=<a>`;
2. **HIT**: повертає збережений JSON, база не задіяна;
3. **MISS**: виконує запити до бази (`COUNT(*)` і сторінку), кладе готовий JSON у Redis
   на `CACHE_TTL_SECONDS` = **30 с** і повертає його.

| Налаштування | Значення |
|---|---|
| Перемикач | змінна `CACHE_ENABLED` (`true`/`false`), у Terraform `var.cache_enabled`; зміна створює нову ревізію |
| TTL | 30 с (`CACHE_TTL_SECONDS`), щоб застарілі дані жили недовго |
| Лічильники | `hits`/`misses` у хеші Redis `cache:stats`, спільні для всіх реплік; `GET /cache/stats`, обнулення `POST /cache/stats/reset` |
| Видно у відповіді | заголовок `X-Cache: HIT`, `MISS` або `OFF` |
| Відмова Redis | таймаут 0.5 с, далі запит іде в базу: кеш не може зламати API |

### Redis як окремий Container App

[`terraform/main/redis.tf`](../terraform/main/redis.tf): застосунок `ca-blog-redis` з
образу `redis:7.4.12-alpine`, рівно 1 репліка, 0.25 vCPU / 0.5 GiB, **внутрішній TCP
ingress** на порту 6379 (ззовні недоступний), пароль (`requirepass`) згенерований
Terraform і переданий як секрет. Persistence вимкнена (`--save '' --appendonly no`), бо
це кеш: після перезапуску він просто порожній. `maxmemory 128mb` з політикою
`allkeys-lru`, щоб Redis витісняв старі ключі, а не падав.

Керований Azure Cache for Redis не використано: найдешевший Basic C0 коштує близько
$16 на місяць, а Redis у Container Apps близько $6 на місяць.

**Знахідка під час налаштування.** Спочатку API підключався до Redis за FQDN
ingress `ca-blog-redis.internal.<домен середовища>`, і всі з'єднання падали з таймаутом
(`/cache/stats` показував `Timeout connecting to server`, кожна відповідь була MISS).
Перевірка зсередини контейнера API (`az containerapp exec`) показала: коротке ім'я
`ca-blog-redis` резолвиться і порт 6379 відкривається, а `.internal.` FQDN дає таймаут.
Наше середовище не internal-only (API має публічний ingress), і в такому середовищі
до TCP-застосунку треба звертатися за іменем застосунку. Тепер
`REDIS_URL = redis://:<пароль>@ca-blog-redis:6379/0`. Завдяки фолбеку на базу під
час цієї проблеми API працював без помилок, тільки без прискорення.

### Що це означає

* **Кешований ендпоінт став у 5 разів швидшим:** p95 `GET /posts` 1080 → 209 мс. HIT
  це один `GET` у Redis і віддача готового JSON, без двох SQL-запитів і без
  серіалізації 20 постів через Pydantic.
* **Прискорились і некешовані ендпоінти** (p95 на 25-37% нижче). Вони стоять у тій
  самій черзі на CPU реплік, а `GET /posts` був найважчим запитом і забирав найбільше
  CPU. Звільнений CPU дістався решті запитів.
* **База отримує вдвічі менше роботи на запит:** 1.54 → 0.77 транзакцій на HTTP-запит.
  Це збігається з розрахунком: без кешу одна ітерація дає ~16.5 звернень до бази, з них
  8 це 4 × `GET /posts` по два SQL-запити (`COUNT` і сторінка). З кешем ці 8 майже
  зникли, лишилось ~8.5, тобто ~0.85 на запит. Через те що запитів стало на 68%
  більше, загальна кількість транзакцій впала лише на 15%, а CPU бази на 14-26%.
* **Hit ratio 99.46%.** У сценарії тільки 2 ключі (`offset=0` і `offset=20`), кожен
  протухає раз на 30 с. За 10 хв це ~40 очікуваних MISS, а було 114: коли ключ
  протухає, кілька реплік одночасно отримують MISS і йдуть у базу (cache stampede, див.
  нижче). При TTL 30 с це ~3 зайві запити раз на 30 с, тому не проблема.
* **Реплік знадобилось стільки ж (до 4), алерт теж спрацював** (11:52:40). Це не
  означає, що кеш не допоміг. Вузьке місце було в CPU реплік, а не в базі, і k6 тут
  замкнена модель: кожен VU чекає на відповідь і одразу шле наступний запит. Швидші
  відповіді означають більше запитів від тих самих 25 користувачів (87.5 замість 52
  запитів/с), і CPU знову впирається в ціль. Правильне порівняння тут **ємність при
  однакових ресурсах**: на 4 репліках з CPU ~75% сервіс обробляв ~5 000 запитів/хв без
  кешу і ~7 800 з кешем, тобто **+55% пропускної здатності**. При фіксованому потоці
  запитів (відкрита модель, як у реальному трафіку) той самий трафік потребував би
  менше реплік.
* **Масштабування з кешем почалось раніше:** 2 репліки через 1 хв 51 с після старту
  (без кешу через 2 хв 28 с), 4 репліки через 4 хв (без кешу через 6.5 хв). Кожен VU
  швидше отримує відповіді і генерує більше навантаження, тому CPU перетинає ціль
  раніше. Після тесту реплік повернулось до 1 о 12:01:26, через ~6 хв після кінця.

**Висновок:** для читацького навантаження «9 читань : 1 запис» кеш на одному
найчастішому і найважчому ендпоінті з TTL 30 с дав 99.5% попадань, у 5 разів знизив p95
цього ендпоінту, удвічі зменшив навантаження на базу на запит і на 55% підняв
пропускну здатність тих самих 4 реплік. Ціна: Redis за ~$0.20 на добу і стрічка, яка
може відставати до 30 с.

## Ціна кешу: застарілі дані

Після запису (`POST`, `PUT`, `DELETE /posts`) кеш **не інвалідується**. Тому список
постів може бути застарілим **до 30 с** (TTL):

* новий пост з'явиться у `GET /posts` не одразу, а після того, як ключ сторінки
  протухне;
* так само `total` у відповіді і видалений або змінений пост у списку;
* `GET /posts/{id}` не кешується, тому сам пост доступний одразу після створення. Саме
  тому сценарій k6 читає щойно створений пост через `/posts/{id}`.

Для блогу 30 с затримки появи поста в стрічці прийнятні. Якщо ні, є варіанти:

| Спосіб | Як | Мінус |
|---|---|---|
| Коротший TTL | 5-10 с | менше hit ratio, база знову отримує більше запитів |
| Інвалідація при записі | після `commit()` видаляти ключі `posts:list:*` | треба знайти всі ключі (`SCAN`), складніше; між записом і видаленням є мить гонки |
| Версія в ключі | лічильник `posts:version` у Redis, `INCR` при кожному записі, версія входить у ключ | старі ключі просто доживають TTL; один зайвий запит до Redis на читання |
| Write-through | при записі одразу перераховувати і класти першу сторінку | кожен запис дорожчий |

При частих записах (у нашому тесті ~5 постів/с) інвалідація при кожному записі майже
зводить кеш нанівець: ключ видаляється частіше, ніж його встигають прочитати. Тоді
TTL-підхід із допустимою затримкою кращий.

Ще один ризик TTL-кешу: **cache stampede**. Коли популярний ключ протухає, усі репліки
одночасно отримують MISS і йдуть у базу. У нас ключів мало і запит дешевий, тож це
кілька зайвих запитів раз на 30 с. При важчих запитах допоможе блокування
(`SET NX`) на час перерахунку або раннє оновлення до закінчення TTL.
